# Reference — This Build vs. kubeadm

Not a build stage — a comparison, for once the cluster is up and you want to understand what kubeadm would have automated.

## Process comparison

| | **This build (manual)** | **kubeadm** |
|---|---|---|
| Certificates | Generated by hand with openssl ([`04-certificates.md`](./04-certificates.md)) | `kubeadm init` generates all of them automatically in one step |
| etcd | Own systemd service ([`07-etcd.md`](./07-etcd.md)) | Runs as a **static Pod** — kubelet starts it from a manifest, not systemd |
| kube-apiserver, scheduler, controller-manager | Each its own systemd service, flags written by hand ([`08-control-plane.md`](./08-control-plane.md)) | Also static Pods, manifests auto-generated by kubeadm |
| kubeconfigs | Built by hand with `kubectl config set-*` ([`05-kubeconfigs.md`](./05-kubeconfigs.md)) | Auto-generated, placed in `/etc/kubernetes/*.conf` |
| Worker joining | Manual cert + kubeconfig + systemd setup ([`09-container-runtime.md`](./09-container-runtime.md), [`10-worker-node.md`](./10-worker-node.md)) | One command: `kubeadm join <ip>:6443 --token ... --discovery-token-ca-cert-hash ...` |
| CNI/networking | Manual static routes, no overlay ([`11-pod-network-routes.md`](./11-pod-network-routes.md)) | You still pick a CNI yourself (Flannel/Calico/etc.) and `kubectl apply` it — not automated even by kubeadm |
| CoreDNS | Manual YAML applied by hand ([`12-coredns.md`](./12-coredns.md)) | Installed automatically as part of `kubeadm init` |
| admin vs super-admin split | Manual — separate certs + RBAC binding ([`14-limited-admin.md`](./14-limited-admin.md)) | `admin.conf` from `kubeadm init` is full `system:masters` by default — you'd add a scoped-down identity yourself the same way we did here |
| Time to a working cluster | Hours | Minutes |

## Folder/file layout comparison

The destinations are strikingly similar — kubeadm follows the **same Linux conventions** this build does, it just automates filling them in.

| Folder | This build | kubeadm |
|---|---|---|
| Certs | `/var/lib/kubernetes/*.crt` + `*.key` (our own layout) | `/etc/kubernetes/pki/*.crt` + `*.key` |
| etcd data | `/var/lib/etcd/` | `/var/lib/etcd/` — **identical path** |
| Control plane component configs | `/etc/kubernetes/config/kube-scheduler.yaml` + our own systemd units | `/etc/kubernetes/manifests/*.yaml` — static Pod manifests for apiserver, controller-manager, scheduler, etcd |
| kubeconfigs | Built in `~/k8s-certs/` on jumpbox, scp'd out | `/etc/kubernetes/admin.conf`, `controller-manager.conf`, `scheduler.conf`, `kubelet.conf` |
| kubelet config | `/var/lib/kubelet/kubelet-config.yaml` (ours) | `/var/lib/kubelet/config.yaml` — same folder, auto-generated |
| CNI config | `/etc/cni/net.d/` | `/etc/cni/net.d/` — **identical path**, populated when you apply a CNI manifest |
| Service definitions | `/etc/systemd/system/*.service` — etcd, apiserver, scheduler, controller-manager **all** as systemd services | Only `kubelet` and `containerd` are systemd services — the rest run as static Pods kubelet itself starts and supervises |

## The one structural difference that actually matters

In this build, **etcd/apiserver/scheduler/controller-manager are systemd services**, managed directly by the OS. **In kubeadm, those same four are static Pods** — kubelet reads YAML from `/etc/kubernetes/manifests/` and kubelet itself keeps them running, not systemd. Only `kubelet` and `containerd` are "real" systemd services in a kubeadm cluster.

This is the main reason "the hard way" is taught at all — building it with systemd first makes it obvious what each component needs (which certs, which flags, which ports) before kubeadm hides all of that behind static Pod manifests and one init command.

## When to actually use which

- **kubeadm** — any real cluster, any environment where you just want Kubernetes running correctly and maintainably. Use this for anything beyond learning.
- **Manual build (this repo)** — purely educational. Nobody runs manual-cert, systemd-etcd clusters in production; the value is entirely in understanding what kubeadm automates under the hood.
